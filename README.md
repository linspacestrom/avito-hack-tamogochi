# Avito Tamagotchi

Проект команды на хакатоне Авито «Лаборатория кода» по кейсу «Авито Тамагочи» —
геймификация с виртуальным питомцем поверх классифайда: пользователь заводит питомца,
ухаживает за ним (кормит, играет), получает опыт и уровни, зарабатывает награды и выполняет
задания, часть которых привязана к реальным действиям в Авито.

Полное описание продуктовых и технических решений — в [ARCHITECTURE.md](ARCHITECTURE.md).

## Статус проекта

### Готово

- Регистрация, вход, JWT-авторизация (access + refresh).
- Питомец: отображение, выбор персонажа, кормление/игра меняют характеристики на фронте,
  состояние сохраняется между сессиями.
- Каталог наград, выдача награды пользователю с защитой от повторной выдачи (unique constraint
  на пользователя и награду).
- Ежедневная награда — зацикленный 14-дневный календарь.
- Задания трёх типов (ежедневные / общие / вне игры на Авито) — список с прогрессом и
  получение награды за выполненное задание, экран наград подключён к этому API.
- Лидерборд, ежедневная сводка, event-based учёт прогресса — реализованы, проходят тесты,
  добираются финальным ревью и мерджем в `main`.

### В работе

- Backend питомца (сервис/эндпоинты) — на фронте характеристики пока считаются и хранятся
  локально, без синхронизации с сервером.
- Backend мини-игры.
- WebSocket-обновления состояния питомца в реальном времени.
- Деградация характеристик питомца по времени.

Подробнее по каждому пункту и ключевым продуктовым компромиссам —
[история решений](ARCHITECTURE.md#история-решений).

## Стек

**Backend:** Go, chi, PostgreSQL, pgx/v5, sqlc, JWT (access + refresh), Swagger.
**Frontend:** React, TypeScript, Vite.

Обоснование ключевых технических решений — в
[ARCHITECTURE.md → Технический стек](ARCHITECTURE.md#технический-стек).

## Структура проекта

```text
avito-hack-tamogochi/
├── backend/
│   ├── cmd/server/           # точка входа
│   ├── internal/             # app, handler, service, repository, домены (rewards, tasks, ...)
│   ├── migrations/           # up/down SQL-миграции
│   ├── docs/                 # generated Swagger
│   └── README.md             # подробная инструкция по backend
└── frontend/
    ├── src/                  # api, components, pages, providers, types, router
    └── package.json
```

Поток HTTP-запроса на backend:

```text
client → chi router → middleware → handler → service → repository → PostgreSQL
```

## Запуск

### Backend

```bash
cd backend
go mod download
# создать backend/.env — шаблон и подробности в backend/README.md
migrate -path migrations -database "$DATABASE_URL" up
go run ./cmd/server
```

API поднимается на `http://localhost:8080`, Swagger — на `http://localhost:8080/swagger/index.html`.
Полная инструкция (переменные окружения, генерация `AUTH_SECRET`, миграции, sqlc) —
в [backend/README.md](backend/README.md).

### Frontend

```bash
cd frontend
npm install
npm run dev
```

Frontend поднимается на `http://localhost:5173` и обращается к backend на `:8080`.

## Особенности реализации

- **Слоистая архитектура backend**: handler → service → repository, с доменными пакетами
  (`rewards`, `tasks`) независимыми от HTTP и от Postgres — конвертация между
  `pgtype`/`uuid` и доменными типами инкапсулирована в repository.
- **sqlc** генерирует типобезопасный Go-код прямо из SQL-запросов и реальной схемы миграций —
  ошибки в SQL ловятся при сборке, а не в рантайме.
- **Атомарность через транзакции** (`go-transaction-manager`): например, получение ежедневной
  награды одновременно продвигает прогресс пользователя и пишет запись в лог истории — либо
  обе операции проходят, либо ни одна.
- **Защита от повторной выдачи наград** — unique constraint `(userId, rewardDefinitionId)` в
  БД, а не только проверка в коде.
- **Разделение одноразовых и циклических наград**: обычные награды (`user_rewards`) защищены
  уникальностью по пользователю и награде; ежедневный календарь наград и выполнение заданий
  переиспользуют одни и те же награды повторно, поэтому у них отдельный append-only лог
  истории, а не запись в `user_rewards`.
- **Список заданий не прячет непройденные** — LEFT JOIN на прогресс пользователя, так что
  задание видно с нулевым прогрессом ещё до первого действия по нему.
- **Задания вне игры (интеграция с Авито)** — заглушки с правдоподобными данными на MVP
  (открыть приложение, разместить объявление, оформить доставку и т.п.), реальная интеграция
  через события/вебхуки — после хакатона.
