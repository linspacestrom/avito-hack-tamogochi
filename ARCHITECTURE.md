# Архитектура проекта

Единая точка правды по продуктовым и техническим решениям. Основная часть ниже — только
актуальное финальное состояние по каждой теме, без слоёв "было/стало". История того, как
менялись решения по датам созвонов — отдельным логом в самом низу, в разделе
[История решений](#история-решений).

## Цель продукта

Создать игровую механику, которая мотивирует пользователя ежедневно возвращаться в Авито.
Питомец — причина ежедневного входа; награды и игровые задания стимулируют пользоваться
основным продуктом Авито (объявления, доставка, категории). MVP не режем — весь функционал
ниже входит в план как есть.

## Пользовательские сценарии

### Основной путь: регистрация → уход за питомцем

1. Регистрация/вход.
2. Создание питомца (имя + выбор персонажа) — отдельный экран после первой авторизации.
   После подтверждения создаётся питомец первого уровня.
3. Короткое обучение: как развивается питомец, как получать опыт, зачем энергия и монеты,
   как работают задания, какие награды доступны, что бонусы применимы внутри Авито.
4. Главный экран: питомец, уровень, опыт, монеты, энергия, настроение, сытость, ежедневная
   награда, список активных заданий. Действия: покормить, сыграть, задания, забрать награды,
   получить ежедневную награду.

### Сессия мини-игры

1. Пользователь нажимает «Играть» → модальное окно (описание, стоимость 20 энергии, кнопки
   «Играть»/«Закрыть»).
2. Фронтенд проверяет наличие энергии → backend повторно валидирует энергию (не доверяем
   фронту) → создаётся игровая сессия → списывается 20 энергии → игра начинается.
3. По завершении фронтенд отправляет набранные очки, backend считает награду (например,
   1 очко = 1 монета, 1 очко = 2 опыта), обновляет статистику, прогресс заданий, проверяет
   достижения, сохраняет лучший рекорд.
4. Экран результатов: «Сыграть ещё» (backend заново проверяет энергию) или «Вернуться в
   меню».

### Получение ежедневной награды

Отдельный экран/API, не совмещён с обычными заданиями. Пользователь забирает награду за
текущий день зацикленного 14-дневного календаря (см. [Награды](#награды)).

### Выполнение задания

Пользователь открывает окно заданий, видит список: название, описание, прогресс, награда,
кнопка получения награды (активна, если выполнено). Прогресс по каждому заданию считается
автоматически по событиям (см. [Задания](#задания)) — пользователь ничего не отмечает
вручную для игровых заданий.

### Возврат после долгого отсутствия

При первом входе за день (после любого перерыва) показывается отчёт — см.
[Ежедневная сводка](#ежедневная-сводка). Усиливает ощущение «живого» питомца и стимулирует
не пропускать входы.

## Характеристики питомца

| Характеристика | Как меняется |
|---|---|
| Уровень | Растёт от опыта; каждый новый уровень открывает аксессуары, повышает ценность наград, открывает кастомизацию |
| Опыт | За вход, игры, кормление, задания, достижения |
| Монеты | За мини-игры, задания, достижения, ежедневные награды; тратятся на еду и аксессуары |
| Сытость | Падает со временем, восстанавливается кормлением (3 вида еды), не превышает 100% |
| Настроение | Растёт от игр и регулярных входов, падает от голода и долгого отсутствия |
| Энергия | Максимум 100, ~20 за одну игру, восстанавливается со временем, может выдаваться как награда |

### Деградация во времени (ленивый расчёт)

Решение с сегодняшнего созвона: сытость/энергия/настроение **не** тикают постоянно в БД.
Хранится только момент последнего действия (например, `lastFedAt`), а актуальное значение
пересчитывается по формуле в момент, когда оно кому-то нужно:

```
минут_прошло = сейчас - lastFedAt
текущее_значение = максимум - (минут_прошло / скорость_деградации)
```

Пересчёт происходит заново при каждом обращении — и при обычном REST-запросе (открыл
главный экран), и когда фоновый процесс раз в 20–30 секунд отправляет обновление в
WebSocket тем, кто сейчас онлайн. **В БД пишется только один раз — когда пользователь
реально что-то сделал** (покормил, поиграл), не постоянно. Воркера, который сам
декрементирует значения в БД для всех пользователей, нет — дороже по нагрузке и не нужно.

Явно формула проговорена на примере сытости (`lastFedAt`), но принцип общий для всех трёх
деградирующих/восстанавливающихся характеристик — энергия и настроение считаются тем же
способом (для энергии — в обратную сторону, регенерация, а не убывание). Названия полей
(`lastMoodAt`, `lastEnergyAt`) — рабочие, финализируются при реализации у
@yzhenevstavlyaet.

### Аксессуары

Каждый новый уровень открывает новые предметы (шапки, очки, одежда, игрушки). До
достижения нужного уровня предмет отображается заблокированным, после — покупается за
монеты.

## Мини-игра

Питомец работает курьером Авито: бегает по экрану с контейнером и ловит падающие предметы.

При появлении предмета генерируется случайное число 0–100:

| Диапазон | Предмет |
|---|---|
| 0–60 | обычный груз |
| 61–85 | бомба |
| 86–100 | брак |

Нужно ловить товары/коробки, избегать бомб/брака/повреждённых товаров. Скорость падения
постепенно растёт по ходу игры. Игровая сессия и расчёт награды — см.
[сценарий выше](#сессия-мини-игры).

## Система еды

При действии «Покормить» открывается окно кухни со списком еды. Каждый продукт — стоимость
+ восстановление сытости. Три вида: обычная, вкусная, премиальная.

Процесс: пользователь выбирает продукт → видит цену и восстановление → backend проверяет
хватает ли монет и не превысит ли итоговая сытость 100% → списываются монеты → повышается
сытость.

## Задания

Открываются отдельным окном. Каждое задание: название, описание, прогресс, награда, кнопка
получения (если выполнено).

Три типа:

| Тип | Примеры |
|---|---|
| Ежедневные | войти сегодня, покормить питомца, сыграть 3 раза |
| Общие / долгосрочные | достичь 10 уровня, заработать 10 000 опыта, сыграть 100 игр |
| Вне игры (Авито) | открыть приложение, посмотреть объявления, разместить объявление, написать продавцу, оформить доставку, добавить в избранное |

**Отслеживание прогресса — через события, не отдельная логика на каждое задание.** Любое
действие пользователя (начало/завершение игры, кормление, получение награды, ежедневный
вход) генерирует `Event`. Единый диспетчер слушает события и инкрементирует `currentValue`
у всех активных заданий, чей `targetMetric` совпадает с типом события — не отдельный
обработчик под каждое задание.

**Задания вне игры (Авито) — сейчас заглушки с правдоподобными моковыми данными**, не
пустая кнопка «отметить выполненным» без контекста. Реальная интеграция с реальными
действиями в Авито — после MVP, через Kafka UI (предложил @yzhenevstavlyaet) и/или вебхуки
(предложил @NBx03).

**Уточнение с ментором (6 авг):** спросили через Google Doc, достаточно ли для MVP хакатона
заглушек на задания/награды, связанные с реальными действиями в Авито (открыть приложение,
разместить объявление, промокоды, скидка на доставку), или нужна хотя бы частичная
интеграция по API/Kafka/вебхукам. Итоговый ответ ментора: то, что уже реализовано в самом
Авито как продукте (эти пользовательские действия — не то, что строит команда на
хакатоне) — можно заглушать; всё остальное, то есть саму новую логику заданий и наград,
которую строит команда, — желательно реализовать по-настоящему, не заглушкой. В любом
случае заглушки должны быть максимально похожи на реальные кейсы, не пустыми и не
случайными — это подтверждает и обосновывает уже выбранный подход выше.

## Награды

Награда — тип, значение, источник получения. Закрепляется за конкретным пользователем.

| Категория | Примеры |
|---|---|
| Игровые | монеты, опыт, энергия |
| Бонусы Авито | промокоды, скидка на доставку, скидки по категориям, бонусы Авито, бонусы Авито Доставки, бонусы Автотеки |

Защита от повторной выдачи одной и той же награды одному пользователю — unique constraint
на `(userId, rewardDefinitionId)` в `UserReward`.

### Ежедневный цикл наград

Отдельная система, не совмещена с обычными заданиями. Это повторяющийся календарь наград на
14 дней: пользователь идёт по дням 1→14, на 14-й день цикл заканчивается и начинается заново
с дня 1 — не разовая последовательность на весь хакатон, а именно зацикленный 2-недельный
календарь. Получение — через отдельный API (`GET /rewards/daily-status`,
`POST /rewards/daily-claim`).

Разделены каталог наград по дням цикла (общий на всех) и прогресс конкретного пользователя
по этому календарю (см. `DailyRewardCycle` и `UserDailyRewardProgress` в
[схеме БД](#схема-бд)) — так и то, и другое можно менять независимо (поменять награду за
день 5 всем пользователям, не трогая прогресс каждого).

> ⚠️ Не решено: при пропуске дня прогресс пользователя по календарю либо сбрасывается на
> день 1, либо замораживается на текущем дне — зависит от бизнес-логики, которую ещё не
> выбрали. Зафиксировать до реализации `POST /rewards/daily-claim`.

энергии, сколько опыта и монет заработано вчера, лучший рекорд мини-игры за день, полученные
награды.

## Auth-контракт

> ⚠️ **Механизм передачи токена не финален.** JWT в httpOnly cookies был решением созвона
> 4 августа, но @yzhenevstavlyaet на созвоне 6 августа сказал, что делать через cookies не
> будет — возникли сложности с реализацией — и сделает по-другому, конкретный механизм не
> назвал. Набор ручек ниже (register/login/refresh/logout/me) остаётся актуальным по составу
> действий, но столбец "Действие" описывает именно cookie-вариант — часть про cookies нужно
> считать устаревшей до уточнения у @yzhenevstavlyaet. На доске Jira задача SCRUM-8 всё ещё
> содержит старое описание с cookies — тоже требует обновления после уточнения.

| Метод | Путь | Вход | Действие |
|---|---|---|---|
| POST | `/api/auth/register` | email, password, displayName | Создаёт пользователя, возвращает user (механизм выдачи токена — уточняется) |
| POST | `/api/auth/login` | email, password | Проверяет пользователя, возвращает user (механизм выдачи токена — уточняется) |
| POST | `/api/auth/refresh` | refresh-токен | Отзывает старую refresh-сессию, создаёт новую пару токенов, возвращает user |
| POST | `/api/auth/logout` | — | Отзывает refresh-сессию |
| GET | `/api/auth/me` | access JWT | Проверяет access JWT, возвращает текущего пользователя |

## Git-workflow

- `main` защищена от прямого пуша.
- Каждый работает в своей feature-ветке.
- Слияние в `main` — через pull request; саморевью и самоодобрение своего PR разрешено.
- Именование веток — префикс по Conventional Commits (`feat/`, `fix/`, `docs/` и т.п.) +
  через дефис короткое описание, например `feat/rewards`, `docs/architecture-day3`. До
  6 августа встречались `feature/...` и ветки без префикса — новые ветки заводить только по
  этому формату, старые не переименовываем задним числом без необходимости.
